# Insert, update and delete data in Milvus

## Tools used

`milvus_get_collection_info`, `milvus_insert_data`, `milvus_delete_entities`, `milvus_query`.

**Upsert is not exposed** by zilliztech/mcp-server-milvus (the connector has an internal upsert, but no MCP
tool). Do not call a `milvus_upsert` tool — it does not exist. Use the delete-then-insert pattern below,
or give the user a pymilvus `client.upsert(...)` snippet for atomic upserts. For document knowledge bases,
`scripts/milvus_kb.py ingest` already upserts by document hash (skill `milvus-knowledge-desk`); for guarded bulk
deletes use `scripts/milvus_ops.py delete-entities` (dry-run first).

## Instructions

1. Call `milvus_get_collection_info` first. Note the primary key name and whether it is `auto_id`,
   the vector field name(s) and `dim`, required scalar fields, and whether the dynamic field is enabled.
2. `milvus_insert_data` takes `data` as a **list of row objects**:

```json
{"collection_name": "docs", "data": [
  {"vector": [0.12, 0.03, ...], "text": "Milvus is a vector database", "source": "intro.md"},
  {"vector": [0.08, 0.11, ...], "text": "Zilliz Cloud is managed Milvus", "source": "cloud.md"}
]}
```

   - Omit the primary key when `auto_id` is true; provide it when false.
   - Every vector must have exactly `dim` floats. **The MCP server does not compute embeddings.** Vectors
     must come from the user's embedding pipeline (code you write/run in the project, or a Milvus 2.6
     server-side embedding function). Never invent or hand-write "embeddings" for real data.
   - For BM25 collections, insert only the text field (plus dense vector if present); the sparse field is
     generated by Milvus — do not supply it.
   - Insert in batches of roughly 100–1,000 rows per call to keep tool payloads small.
3. Verify with `milvus_query` (e.g. `filter_expr: "source == \"intro.md\""`, `limit: 5`).
4. **Update / upsert pattern** (not atomic):
   1. `milvus_delete_entities` with `filter_expr: "pk in [\"a1\", \"a2\"]"` (or `id in [1, 2]`)
   2. `milvus_insert_data` with the new versions (same explicit primary keys)
   Warn the user that a reader may briefly miss these rows between the two calls.
5. **Delete**: `milvus_delete_entities` with a filter expression. Before deleting, run the same filter
   with `milvus_query` and show the user how many/which rows match; ask for confirmation if the delete is
   broad. Never pass an empty or always-true filter unless the user explicitly asked to clear everything.

## Filter expression cheatsheet

`tag == "db"`, `year >= 2024 and lang in ["en", "zh"]`, `id in [1, 2, 3]`,
`text like "Milvus%"`, `meta["author"] == "alice"` (JSON / dynamic field),
`array_contains(tags, "rag")`, `created_at > 1760000000`.
