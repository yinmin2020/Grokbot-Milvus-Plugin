# milvus-insert-data

## Execution and configuration

Resolve `PLUGIN_ROOT` to the plugin directory containing `pyproject.toml`, two levels above this SKILL.md. Use an absolute path. The user's current directory may be a different project. Run scripts as:

```bash
uv run --project "$PLUGIN_ROOT" "$PLUGIN_ROOT/scripts/SCRIPT.py" --help
```

Replace SCRIPT with the entry point below. Connection settings are process environment variables: `MILVUS_URI` (default `./milvus.db`), `MILVUS_TOKEN`, and `MILVUS_DB` (default `default`). Use an absolute Lite path for repeatable connections from different working directories. The database lives on the machine executing the script. Every script closes its client before exiting; serialize commands sharing a Lite path.

Respect `OPS_PROTECTED_COLLECTIONS` and `OPS_WRITE_ALLOW_PREFIX` for every write. Confirm the user's intended collection and action before destructive changes; existing explicit authorization is sufficient. Do not print tokens or embed them in commands. Inspect `--help` for argument details. Do not invent commands or fall back to generated database code.

## Workflow

Use `milvus_data.py upsert`. The UTF-8 JSON file contains an array of objects with a stable string `pk`, `text`, optional JSON object `metadata`, and a `dense` array for dense/hybrid collections. Sparse vectors are generated by Milvus's BM25 function. Use the same embedding model and dimension for every document and query; the generic data toolkit accepts vectors and does not call an embedding provider.

```json
[{"pk":"article-1","text":"Milvus supports native BM25.","metadata":{"lang":"en"}}]
```

This example is for a BM25-only collection. Add real embedding vectors for dense/hybrid collections.

```bash
uv run --project "$PLUGIN_ROOT" "$PLUGIN_ROOT/scripts/milvus_data.py" upsert --collection articles --file /absolute/path/rows.json
uv run --project "$PLUGIN_ROOT" "$PLUGIN_ROOT/scripts/milvus_data.py" upsert --collection articles --file /absolute/path/rows.json --execute
```

The first command validates and previews. The second uses native upsert with deterministic caller-provided keys. A failed batch can be retried with the same IDs. Never implement replacement by deleting first. Multi-batch writes are not transactional. For document files use `milvus_kb.py ingest`; for user memory use `milvus_memory.py remember` with a user ID.
